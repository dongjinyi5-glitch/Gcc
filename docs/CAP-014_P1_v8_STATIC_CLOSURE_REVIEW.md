### F-01（P0）`VERIFIED_MANUAL` 永不满足 `WRITE_PERMITTED`，`CP-R` 路径失去意义

**位置**：`A.7.8`（行 639–655，关键行 644–646）、`A.10.1` PWA-6（行 826）

**原文摘录**（行 643–646）：
```
  WAL_STATE_COMPLETE == YES
  AND CHECKPOINT_STATUS ∈ {VERIFIED, ABSENT_CLEAN}
  AND (CHECKPOINT_STATUS == VERIFIED_MANUAL 仅当：manual_epoch != null
       AND 人工已在签核中明确接受该 epoch 下的写入（BLK-5 已决）)
```

**成因**：第 2 行把 `CHECKPOINT_STATUS` 限定为 `{VERIFIED, ABSENT_CLEAN}`；第 3 行是形如"`P` 仅当 `Q`"的**蕴含约束**（`P→Q`），不是"`P` 也在允许集合内"的**授权**。两者合取后，`status == VERIFIED_MANUAL` 时第 2 行恒假 → `WRITE_PERMITTED` 恒为 `NO`。同一缺陷存在于 `PWA-6`（`∈ {VERIFIED, ABSENT_CLEAN}` + 同款括号子句）。同时 `A.7.1` 的 `YES` 行（行 532）已把 `VERIFIED_MANUAL` 纳入集合，`A.5.10` 末句与 `A.22` BLK-5 行也预设"`VERIFIED_MANUAL` 下可以写入"——三处与 `A.7.8` / `PWA-6` 互斥。

**可执行修法**（替换行 644–646）：
```
  AND CHECKPOINT_STATUS ∈ {VERIFIED, VERIFIED_MANUAL, ABSENT_CLEAN}
  AND (CHECKPOINT_STATUS != VERIFIED_MANUAL
       OR (manual_epoch != null
           AND BLK-5 == DECIDED_ACCEPT
           AND 签核记录中已明确接受该 epoch 下的写入))
```
`PWA-6` 同步替换为：
```
PWA-6 | `WAL_STATE_COMPLETE == YES` ∧ `CHECKPOINT_STATUS ∈ {VERIFIED, VERIFIED_MANUAL, ABSENT_CLEAN}` ∧ (`CHECKPOINT_STATUS != VERIFIED_MANUAL` ∨ (`manual_epoch != null` ∧ BLK-5 == DECIDED_ACCEPT ∧ 签核接受该 epoch)) ∧ `WAL_IDENTITY_STATUS ∈ {IDENTITY_VERIFIED, IDENTITY_NOT_APPLICABLE}` ∧ `FAILURE_LOG_STATUS ∈ {FAIL_READABLE_EMPTY, FAIL_ABSENT_CONSISTENT}` | PASS / FAIL / UNKNOWN
```

**受影响用例**：`S15c`（期望 `READY`，但若同时断言"允许写入"则当前文档不成立）。**建议为 `S15c` 增断言 ⑥**："`WRITE_PERMITTED == YES`（在 BLK-5 已决且签核接受该 epoch 的前提下）"。

**影响**：统计 **+1 断言**（专项 235 → 236）；执行边界**不变**（仍为禁止真实写入）；写入权限**修正后**才可能为 `YES`，修正前恒为 `NO`。

### F-02（P0）身份类故障的 `MANUAL_BLOCKED` 无任何可达出口

**位置**：`A.5.10` CR-6（行 445）、`A.7.4`（行 585）、`A.15` #10（行 1055）、`A.5.7.4` 硬规则（行 372）

**原文摘录**：
- 行 445：`| CR-6 | WAL 身份可得（IDENTITY_VERIFIED）——**IDENTITY_UNVERIFIABLE 时禁止 CP-R** |`
- 行 585：`| **MANUAL_BLOCKED** | **READY** | **仅人工 T5（三阶段全部完成）** | OP_UNRESOLVED == ∅ + MP-1 证据 + MP-2 签核 + MANUAL_RESET 持久 + **CP-R 成功（VERIFIED_MANUAL）** + 重新扫描 YES 且 V-T 通过；**无任何自动出口** |`
- 行 372：`**硬规则**：IDENTITY_MISMATCH / IDENTITY_UNVERIFIABLE 时**不得自动推进 durable checkpoint，不得允许新写入**。`

**成因**：`IDENTITY_MISMATCH` / `IDENTITY_UNVERIFIABLE` 是 `MANUAL_BLOCKED` 的**规范入口**（行 368–369、行 370）；`MANUAL_BLOCKED → READY` 的**唯一**出口要求 `CP-R` 成功；`CR-6` 又禁止在身份不可得时执行 `CP-R`。三点构成闭环：**身份类故障进入 `MANUAL_BLOCKED` 后，文档规定的所有出口都不适用**。`A.7.4` 结论段的论证"`MANUAL_BLOCKED` 没有自动出口，只有人工出口"因此对身份类故障**不成立**——真实情况是"没有出口"。这是一个**过严**缺陷（不会让不安全状态通过），但会让"身份不一致"这一最高频的真实故障场景**永久停摆**，且文档把它描述成"可人工恢复"，属于**虚假可达性**。

**可执行修法**：把 `CR-6` 拆成三类，并在 `A.7.4` 增一行显式声明"无出口"：
```
| CR-6 | 身份前提按故障类别区分：
        (a) 故障本身为身份类（IDENTITY_MISMATCH / IDENTITY_UNVERIFIABLE）→ **CP-R 禁止**；
            该情形下 MANUAL_BLOCKED **不存在任何出口**（既无自动、也无 CP-R），
            唯一处置是 BLK-1 决策后由人工在**不重建检查点**的前提下另行授权，
            文档不提供该路径（显式声明为"无出口"，不得表述为"可经 T5 恢复"）；
        (b) 故障非身份类（检查点 INCONSISTENT / 故障日志不可读等）且身份可得 → CP-R 允许；
        (c) 故障非身份类但身份不可得 → **CP-R 禁止**，同 (a) 处置 |
```
`A.7.4` 增行：
```
| **MANUAL_BLOCKED（身份类）** | **无出口** | — | `IDENTITY_MISMATCH` / `IDENTITY_UNVERIFIABLE` 下 `CP-R` 被 CR-6(a) 禁止；**不得表述为"可经 T5 恢复"**；待 BLK-1 决策 |
```
`A.15` #10 的"允许的下一步"列同步改为"**无文档化出口**；待 BLK-1 决策"。

**受影响用例**：`S15c`（须限定"非身份类故障"前提）；**新增 `S15f`**：`MANUAL_BLOCKED` + `IDENTITY_MISMATCH` + 完整签核 → 断言 `CP-R` 被拒绝（CR-6a）、`CHECKPOINT_STATUS` 保持 `INCONSISTENT`、**不得进入 `READY`**、**不得声称已恢复**。

**影响**：统计 **+1 用例 / +3 断言**（89 → 90，235 → 238）；执行边界**不变**；写入权限**不变**（该路径本就不放行）。

### F-03（P0）`CP-R` 的"不覆盖"发布语义与 `CP-R` 的目的自相矛盾

**位置**：`A.5.10` CR-e（行 455）、`A.11.1`（行 852–872）

**原文摘录**（行 455）：
```
CR-e  "目标不存在才创建"语义发布（不覆盖已有文件；若同名已存在 → 中止，见 A.11）
```

**成因**：`CP-R` 的定义是"**唯一**能把 `INCONSISTENT` 检查点替换为可用检查点的路径"（行 434）。而 `INCONSISTENT` 检查点的**文件必然已存在**（它就是被判定不一致的那个文件）。`CR-e` 要求"同名已存在 → 中止"→ **`CP-R` 在任何真实触发场景下都必然中止**，永远无法产出 `VERIFIED_MANUAL`。根因是把 `A.11.1` 针对**不可变快照证据**的"同名永不覆盖"（那里是正确的：覆盖会销毁唯一证据）原样搬到了**必须可更新**的检查点上。检查点与快照的证据学性质不同：快照是"一次写入、永久只读"；检查点是"多代更新、旧代可弃但须可追溯"。

**可执行修法**（替换 CR-e 为三步）：
```
CR-e  检查点发布语义（**与 A.11.1 的快照发布不同，不得混用**）：
      ① 若 <key>.durable.json **不存在** → 用"不存在才创建"发布（同 A.11.1 ⑤）；
      ② 若**已存在** → 先按 CP-4 同等要求复核身份与旧文件可解析性，再把旧文件
         **原子改名**为 <key>.durable.json.pre_manual.<manual_epoch_id>
         （**改名不是覆盖：旧内容完整保留、可回读、可作为证据**），
         随后用"不存在才创建"发布新文件；
      ③ 改名失败或旧文件不可解析 → **中止**，CHECKPOINT_STATUS 保持 INCONSISTENT；
      ④ **禁止**用 os.replace / MoveFileEx(REPLACE_EXISTING) 直接覆盖旧检查点
         （那样会销毁 pre_rebuild_checkpoint_status 的对照物）。
```
并在 `A.11.1` 的禁止清单旁加一句边界说明：
```
> **适用范围**：本节的"同名永不覆盖"适用于**快照内容文件与 sidecar**（不可变证据）。
> **检查点的更新语义见 A.5.10 CR-e**——检查点必须可更新，其"不销毁旧证据"由
> 旧代改名保留实现，而不是由"禁止覆盖"实现。
```

**受影响用例**：`S15c`（当前无法构造成功路径）；**新增 `S10e`**：检查点已存在（`INCONSISTENT`）+ 完整 MP-1/MP-2 + `MANUAL_RESET` 持久 → 断言 ① 旧检查点被改名为 `pre_manual.<epoch>` 且**内容可回读、哈希不变**；② 新检查点 `manual_epoch` 非空、`pre_rebuild_checkpoint_status == "INCONSISTENT"`；③ 未使用 `os.replace`；④ 目录中**不存在**被覆盖的痕迹（旧文件字节仍在）。

**影响**：统计 **+1 用例 / +3 断言**；执行边界**不变**；写入权限**不变**（修正后才可能走通）。

### F-04（P0）`CreateFileW(CREATE_NEW)` 直接写最终名会留下"名字已占用、内容不完整"的不可恢复快照

**位置**：`A.11.1` ⑤（行 862–864）、禁止清单（行 874–881）

```
     通用：os.link(tmp, final) → 成功后 unlink(tmp)
```

**成因**：`CREATE_NEW` 只保证"**创建**是原子的、且不覆盖"，**不保证内容已就绪**。该分支在**最终名**上先占名、后写内容、再 fsync。崩溃窗口内磁盘状态是：**最终名已存在、内容不完整（甚至 0 字节）、无 sidecar**。后果链：
1. 下次运行看到"同名已存在" → `SNAPSHOT_CONFLICT`；
2. 因"同名永不覆盖"，该名**永久不可再发布**；
3. 因"不自动删除"，该残file**永久不可清理**；
4. → 该 target **永久不可写**，且文档没有任何出口（`A.11.3` 只提供"人工判定"，不提供"授权删除"）。

同时该分支**绕过了** ①②③ 的"tmp 写 → flush+fsync → 全文件 SHA-256 校验"三道保证——它把内容写进最终名，等于取消了 tmp 阶段的意义。

**可执行修法**（替换行 862–866）：
```
⑤ 原子"不存在才创建"发布（**禁止在最终名上直接写入内容**）：
     Windows：MoveFileExW(tmp, final, 0)      ← **不带** MOVEFILE_REPLACE_EXISTING
              目标已存在 → 返回 FALSE / ERROR_ALREADY_EXISTS，**不覆盖**
              要求 tmp 与 final **位于同一卷**（本方案中同目录，天然满足）
     通用：os.link(tmp, final) → 成功后 unlink(tmp)
              目标已存在 → FileExistsError；跨卷 → OSError(EXDEV) → 改用 MoveFileExW
     两机制均不可用 → 记 SNAPSHOT_PUBLISH_UNSUPPORTED（**不是** SNAPSHOT_CONFLICT），
              本次写入终止；该用例记 UNCOVERED，**安全失败**
```
禁止清单增一行：
```
| **（v8.1）用 `CreateFileW(CREATE_NEW)` 打开最终名后向其写入内容** | 名字先占用、内容后写；崩溃后留下"看似已发布但内容不完整"的文件，且因同名永不覆盖而永久不可恢复 |
```

**受影响用例**：`S1c`（须区分"发布失败"与"机制不支持"）；**新增 `S1i`**：`MoveFileExW(tmp, final, 0)` 在目标已存在时返回 `ERROR_ALREADY_EXISTS` → 断言 ① `SNAPSHOT_CONFLICT`；② 既有文件字节**逐字节不变**；③ tmp 保留；**新增 `S1j`**：`os.link` 返回 `EXDEV` → 断言**不得**判 `SNAPSHOT_CONFLICT`，须判 `SNAPSHOT_PUBLISH_UNSUPPORTED` 并安全失败。

**影响**：统计 **+2 用例 / +4 断言**；执行边界**不变**；写入权限**不变**（修正前该 target 会永久卡死，属"过严 + 不可恢复"）。

- **四个集合两两互斥**

**单项上界**（各自独立成立）：

| 条件 | 度量 | 上界 |
|---|---|---|
| 仅 M9 缺失 | 可执行 | 89 − 8 = **81** |
| 仅 `tool_sha256` 缺失 | 可完全通过 | 89 − 8 = **81** |
| 仅 BLK-1 未决 | 可完全通过 | 89 − 4 = **85** |
| 仅 BLK-5 未决 | 可完全通过 | 89 − 1 = **88** |

**联合上界**：

| 条件组合 | 并集 | 上界 |
|---|---|---|
| M9 + `tool_sha256` | 16 | **73** |
| M9 + `tool_sha256` + BLK-1 | 20 | **69** |
| 全部四项 | 21 | **68** |

**文档的 `81 → 77 → 76` 链条复现**：`89−8 = 81`；`81−4 = 77`；`77−1 = 76`。**算术自洽 = True**。

**但该链条存在三处口径问题**：

1. **两个 `81` 是不同集合**。第 1 行的 `81` 来自 M9（可执行），第 2 行的 `81` 来自 `tool_sha256`（可完全通过）。两者数值相同、集合不相交、**度量不同**。文档把它们写成两行并列，随后"上界降为 77（81 − 4）"里的 `81` **未指明是哪一个**。因两集合与 BLK-1 均不相交，数值上两种取法都得 77，但**推理依据不同**，读者无法判断"若 M9 与 `tool_sha256` 同时缺失，上界是多少"。

2. **77 / 76 是条件链，不是并列单项**。若把四行读成"四个独立的单项上界"，会得出"BLK-1 未决 → 77"，而真实单项值是 **85**；"BLK-5 未决 → 76"，真实单项值是 **88**。这两个数只有在**先接受 81 这个前提**后才成立。

3. **度量嵌套未声明**。`可完全通过 ⊆ 可执行 ⊆ 89`。文档在一行里用"可执行"、下一行用"可完全通过"，然后在后续行只写"上界"，跨度量做减法。严格说，"可执行 81 减去 4 条无法通过的用例"得到的是"可完全通过 77"，这一步**恰好**正确，但需要读者自行补上嵌套关系。

4. **未给联合上界**。四条件同时成立的正确上界是 **68**（并集 21），文档未给。若有人用 76 作为"最坏情况覆盖率"，会**高估 8 条**。

→ **F-09（P1）**，修法见 §4 F-09。

## 6. 各条件下"可执行 / 可完全通过 / 部分通过 / UNCOVERED"的依据

> 本节把四个度量**分开定义**，并给出每个条件下的判定依据。这是 C2 要求"区分四种状态、计算单项与组合条件上界、不得把两个单项上界当成联合上界"的正式回答。

### 6.1 四个度量的定义

| 度量 | 定义 | 前提 |
|---|---|---|
| **可执行** | 用例能够被**运行**并产出观察结果 | 依赖的注入手段 / 钩子存在；不依赖被测机制是否正确 |
| **可完全通过** | 运行后**全部**断言为 `PASS` | 可执行 ∧ 被测机制已实现且正确 ∧ 平台前提成立 |
| **部分通过** | 运行后**部分**断言为 `PASS`，其余为 `FAIL` 或 `N/A` | 可执行 |
| **`UNCOVERED`** | 用例**无法构造**或**无法运行**，因而没有任何断言被评估 | ¬可执行（缺钩子 / 缺注入手段 / 平台不支持 / 模型内不可达） |
| **`NOT EXECUTED`** | 用例已设计但**本轮未运行**（当前全部 89 条的状态） | 与上述四者正交：任何用例在未运行前都是 `NOT EXECUTED` |

**关键约束**：`UNCOVERED` **不是**"通过"，也**不是**"部分通过"；`N/A` **不计为通过也不计为失败**（`A.19.1` 开头明文）。

### 6.2 各条件下的判定依据表

| 条件 | 受影响用例 | 可执行 | 可完全通过 | 部分通过 | `UNCOVERED` | 依据 |
|---|---|---|---|---|---|---|
| **无附加条件**（全部机制已实现、平台前提成立） | 0 | 89 | **89** | 0 | 0 | 理论上界；实际须由执行给出 |
| **M9 钩子（H1–H6）缺失** | 8（S5 全部） | **81** | ≤81 | 0 | **8** | `S5` 全部依赖 H1–H6 注入外部写入；无钩子则**无法构造并发窗口**，按 `A.17` S5 末句"无对应钩子 → `UNCOVERED`" |
| **`tool_sha256` / `deps` 未建立** | 8（S2、S3a–c、S7c-1、S7c-2、S7d、S8g） | 89 | **81** | 8（"重做验证"断言无法评估） | 0 | 这些用例的 `REDO_VERIFIED` 断言要求"载荷哈希、`args_digest`、`tool_sha256`、`deps` 四项一致"（`A.13`）；机制未建立 → 该断言无法 `PASS`，只能"部分通过" |

| **M9 + `tool_sha256`** | 16 | 81 | **73** | 8 | 8 | 两集合互斥，并集 16 |

| **模型内不可达组合**（"位于已完成前缀且随后仍被覆盖"） | 0 | — | — | — | 声明为 `MODEL_UNREACHABLE` | `A.21` 末段；**不构造用例、不污染统计** |
| **平台不支持原子不覆盖发布**（F-17 / F-04） | `S1c` / `S1j` | — | — | — | **记 `UNCOVERED` + 安全失败** | 见 §4 F-04 / F-17 修法 |

### 6.3 不得混淆的三组关系

1. **`可执行` ≠ `可完全通过`**：M9 缺失时 `可执行 = 81`，但 `可完全通过` 还需被测机制正确，理论上界同为 81，实际只会更低。
2. **`UNCOVERED` ≠ `部分通过`**：`UNCOVERED` 意味着**零断言被评估**；`部分通过` 意味着**有断言被评估且部分 PASS**。把 `UNCOVERED` 计入"部分通过"会虚增覆盖率。
3. **`NOT EXECUTED` 与上述四者正交**：当前 89 条全部 `NOT EXECUTED`，因此**上述任何"可完全通过 = N"都只是设计上界，不是实测结果**。
